# 原理：从视频到 Spine 骨骼动画

本文说明本工具如何把一段**人物视频**变成一份可在 Spine 里播放的**骨骼动画工程**，
每一段都给出数学定义、实现位置（Rust/TS 文件）以及与原版 Unity 工具 SpineVExt 的对应关系。

---

## 1. 总览

输入：一段视频（本地文件或摄像头流）。
输出：`<工程名>.json`（Spine 4.3 skeleton JSON）+ `<工程名>.atlas` + `<工程名>.png`（图集），
另含导出文件名沿用原版的 `spineOutput.json` 约定。

整条流水线的分工：

```
HTML <video>
   │  TS：src/core/video.ts      逐帧 seek → drawImage → getImageData（RGBA）
   ▼
RGBA 帧 (Uint8ClampedArray)
   │  Rust：preprocess.rs / (MoveNet 路径) preprocessMovenet
   ▼
模型输入张量（NHWC int32 原始像素 / NCHW f32 归一化）
   │  TS：src/core/inference.ts   onnxruntime-web 前向（与原版 Unity.Barracuda 同一角色）
   ▼
原始输出张量（[1,1,17,3] / heatmap+offsets）
   │  Rust：decode.rs / movenet 解码       → 17 个关键点（源图像素坐标 + 置信度）
   ▼
Pose2D[]（每帧）
   │  Rust：smooth.rs                      → 置信度加权 + 圆周角度平滑
   ▼
平滑后的 Pose2D[]
   │  Rust：rig.rs                         → 13 根骨骼的局部旋转角
   ▼
BoneFrame[]
   │  Rust：animate.rs                     → 基准帧选取、缺失传播、静止姿态
   ▼
AnimationData { skeleton, frames[][], validity }
   │  Rust：spine.rs / atlas.rs            → Spine JSON + atlas 文本 + 帧装箱
   ▼
<name>.json / <name>.atlas / <name>.png
```

**所有算法都在 Rust 里**（`crates/spinevext-core`），编译成 `wasm32-unknown-unknown`，
由 `wasm-bindgen` 暴露给 TypeScript；TS 只负责视频解码、推理会话、画布渲染、文件读写。

与原版的角色对照：

| 原版（Unity）                                                | 本实现                             | 说明                          |
| ------------------------------------------------------------ | ---------------------------------- | ----------------------------- |
| `AVProVideo` + `VideoPlayer`                                 | `src/core/video.ts`                | `<video>` + Canvas 抽帧       |
| `DeepLearningImageProcessor` + `NormalizeImage` 计算着色器   | `preprocess.rs`                    | 等比缩放 + 居中裁剪 + 归一化  |
| `PoseNetPoseEstimator`（`Unity.Barracuda`）                  | `inference.ts` + `onnxruntime-web` | 同一角色：跑 ONNX 图          |
| `DecodeSinglePose` / `DecodeMultiplePoses`                   | `decode.rs`                        | heatmap+offset 解码、多人 NMS |
| `AngleSmoothing`（`angleBuffer`/`SmoothAngle`/`ClampAngle`） | `smooth.rs`                        | 圆周角度平滑                  |
| `HumanPoseToBones` / `GenerateBonesForFrame`                 | `rig.rs`                           | 关键点 → 骨骼局部角           |
| `GetBaseFrame` / `baseBones` / `PropogateList`               | `animate.rs`                       | 基准帧与缺失传播              |
| `JSONModels/Spine.cs`                                        | `spine.rs`                         | Spine JSON 数据模型           |
| `CurrentBoneLayoutToTexture` / `CenterImagesInCanvas`        | `atlas.rs`                         | 帧装箱与 `.atlas`             |
| `SaveJsonOutput`                                             | `src/core/export.ts`               | 打包下载                      |

## 2. 视频取帧：把时间轴变成帧序列

浏览器没有逐帧解码 API，所以用「seek + 绘制 + 读像素」：

1. `HTMLVideoElement` 载入用户文件（`URL.createObjectURL`）或摄像头流（`getUserMedia`）。
2. 设定 `video.currentTime = t`，等待 `seeked` 事件（浏览器保证画面已更新）。
3. `ctx.drawImage(video, 0, 0, w, h)` 后 `ctx.getImageData(...)` 得到 RGBA8 数据。

采样策略：按 `detectEveryNFrames` 抽帧，第 `k` 个**检测帧**对应视频帧号
`frameIndex = startFrame + k * detectEveryNFrames`，时间 `t = frameIndex / fps`。
输出动画的时间轴一律使用 `t`（秒），所以「每 N 帧检测一次」不会改变动画时长，只改变采样密度。

原版对应：`DetectPerFrame`、`VideoStartOffset`、`VideoEndOffset`、`Player.frame` 的推进逻辑
（原版日志里的 `Incorrect frame increment going to: {0} - currentFrame: {1}` 就是在处理这个跳帧推进）。

## 3. 预处理：从像素到模型输入

### 3.1 几何：两条等比缩放路径

模型输入是固定尺寸（MoveNet 为 192×192），而视频通常是 16:9。直接拉伸会让人体比例失真，
因此按模型家族的训练习惯做等比缩放，两种几何都归一到同一个 `ImageTransform`：

| 路径                 | 几何                                | 公式                                              | 用途                                                               |
| -------------------- | ----------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------ |
| **cover + 居中裁剪** | `scale = max(dstW/srcW, dstH/srcH)` | `offsetX = (dstW - srcW·scale)/2`，`offsetY` 同理 | heatmap 家族（原版 `CalculateInputDims` / `CropInputDims` 的语义） |
| **letterbox + 补边** | `scale = min(dstW/srcW, dstH/srcH)` | 同上偏移公式；落在源图外的像素补 0（黑边）        | MoveNet（等价 TensorFlow 的 `resize_with_pad`）                    |

这组 `(scale, offsetX, offsetY)` 就是 `ImageTransform`：heatmap 路径用 `preprocess::transform_for`，
MoveNet 路径由 `preprocess::preprocess_letterbox` **和数据一起返回**，解码时必须传回同一个值。
缩放采样用**双线性插值**（4 邻居加权），边界 clamp。

解码时必须用**同一组**参数的逆变换把模型坐标映射回源图像素：

```
srcX = (modelX - offsetX) / scale
srcY = (modelY - offsetY) / scale
```

镜像（`flipX`）在**预处理阶段**翻转图像，而不是解码后再翻坐标——否则关节点会与画面左右错位。

### 3.2 两条输入路径

不同 ONNX 导出的预处理约定不同，因此 Rust 提供两个函数：

| 模型家族                | Rust 函数             | 张量                           | 数值                                          |
| ----------------------- | --------------------- | ------------------------------ | --------------------------------------------- |
| MoveNet（本项目内置）   | `preprocessLetterbox` | `[1,192,192,3]` **int32 NHWC** | 原始 0..255 RGB，归一化在计算图内部           |
| PoseNet（heatmap 家族） | `preprocess`          | `[1,3,H,W]` f32 NCHW           | `pixel/255 - mean[c]`（`scale=255`, `std=1`） |

归一化常量沿用原版 Unity 资源里 `resnet50-posenet-normalization-stats` 的值：

```json
{ "mean": [0.482941176, 0.454509803, 0.404156862], "std": [1.0, 1.0, 1.0], "scale": 255.0 }
```

## 4. 姿态估计网络

### 4.1 模型

内置模型是 **MoveNet SinglePose Lightning** 的 ONNX 导出（CenterNet + MobileNetV2-FPN backbone）：

- 输入：`input`，`int32[1,192,192,3]`（NHWC，0..255 RGB）。
- 输出：`output_0`，`float32[1,1,17,3]`，每个关键点三元组 **(y, x, score)**。
- `y, x` 是**相对模型输入的归一化坐标**（0..1），`score` 已经过 sigmoid。
- 17 个关键点的顺序与 COCO / 原版 PoseNet 完全一致：
  `nose, leftEye, rightEye, leftEar, rightEar, leftShoulder, rightShoulder, leftElbow, rightElbow,
leftWrist, rightWrist, leftHip, rightHip, leftKnee, rightKnee, leftAnkle, rightAnkle`。

> 为什么不是原版那个 ResNet50-PoseNet？原版的 ONNX 权重在 Unity 构建里被 Barracuda
> 以自己的序列化格式重新编码（`sharedassets0.assets` 里只剩 layer/常量结构，没有可直接
> 复用的 ONNX 字节）。MoveNet 与它同为 17 关键点、同 COCO 顺序、单人输出，
> 体积从 ~90 MB 降到 9.4 MB，更适合浏览器。

### 4.2 实测（真实照片，ORT wasm 单线程）

```
input  → int32[1,192,192,3]      output_0 → float32[1,1,17,3]
前向耗时 ≈ 116 ms/帧
nose      y=0.27 x=0.78 score=0.601
lEye      y=0.25 x=0.81 score=0.630
rShoulder y=0.43 x=0.64 score=0.520
lKnee     y=0.98 x=0.84 score=0.047
```

（该照片是两人合影，MoveNet 单人模型在画面右侧人物上给出稳定检测，符合预期。）

### 4.3 PoseNet heatmap 路径（可选）

MoveNet 走 `decode_regression`：`(y_norm, x_norm, score)` → `x = x_norm · 192`、`y = y_norm · 192`
→ 用同一份 `ImageTransform` 逆变换回源图像素。

若用户替换成带 heatmap 的 PoseNet 系模型，走 `decode.rs`：

1. 每个关节点在 `heatmap` 上取全局最大值位置，置信度 `sigmoid(heatmap)`；
2. 用同位置的 `offsets` 修正到亚像素：`x = gridX * stride + offsetX`；
3. 多人模式按分数贪心取根节点，用 `displacements_fwd/bwd` 把同一人的关节点聚成一个人；
4. NMS 半径剔除重叠候选（`nmsRadius`、`maxPoses`）。

张量排布（`nhwc`/`nchw`）与 offset 顺序（`yx`/`xy`）都是 `DecodeConfig` 的可配置项，
因为不同导出的 TF→ONNX 模型这两点不一致。

## 5. 平滑：把逐帧噪声压下去

两件事分开做（`smooth.rs`）：

1. **笛卡尔坐标**：关节点按置信度加权移动平均，窗口半径 `bufferSize`；
   只在窗口内**高置信度**样本上求平均，避免把轨迹拉向原点。
2. **角度**：角度是圆周量，`179°` 与 `-179°` 的算术平均是 `0°`（错误）。
   因此先把角度转成单位圆向量 `(cosθ, sinθ)` 求和再 `atan2` 回来，得到正确的圆周平均。

```
θ̄ = atan2(Σ wᵢ sinθᵢ, Σ wᵢ cosθᵢ)
```

`bufferSize <= 1` 时不做平滑（等价于直通），便于对比调试。
`clamp_angle` 把结果归一化到 `(-180, 180]`。

## 6. 姿态 → 骨骼

### 6.1 骨骼树

14 根骨骼，`rig.rs::BONE_NAMES` 固定顺序，父子关系 `BONE_PARENTS`：

| 骨骼           | 父         | 由哪些关键点决定          | 长度                     |
| -------------- | ---------- | ------------------------- | ------------------------ |
| `root`         | —          | 左右髋中点                | 0（根）                  |
| `hip`          | root       | 髋中心（骨盆）            | 0                        |
| `torso`        | hip        | 髋中心 → 颈（左右肩中点） | 躯干长度                 |
| `head`         | torso      | 颈 → 鼻/眼耳推定头顶      | 头长（≥ 躯干长度 ×0.25） |
| `upperArm.L/R` | torso      | 肩 → 肘                   | 上臂长                   |
| `lowerArm.L/R` | upperArm.* | 肘 → 腕                   | 前臂长                   |
| `upperLeg.L/R` | hip        | 髋 → 膝                   | 大腿长                   |
| `lowerLeg.L/R` | upperLeg.* | 膝 → 踝                   | 小腿长                   |
| `foot.L`       | lowerLeg.L | 小腿延长方向              | 小腿长 ×0.5              |
| `foot.R`       | lowerLeg.R | 小腿延长方向              | 小腿长 ×0.5              |

`hip` 刻意保持与画面坐标对齐（旋转恒为 0），躯干倾角由 `torso` 承载。这样在 Spine 里
`torso` 的 `rotate` 曲线是"活的"，双腿也挂在骨盆这个静止原点上，符合常见绑定习惯；
如果让骨盆跟随躯干，`torso` 的局部角会恒为 0，导出后在 Spine 里看不到躯干动画。

### 6.2 角度与局部旋转

视频像素坐标是 **y 向下**，而数学上的 `atan2` 习惯 **y 向上**，所以取点时就做一次翻转
`y' = imageHeight - y`，之后所有角度都是标准 `atan2(dy, dx)`，单位为度。

Spine 的骨骼 `rotation` 是**相对父骨骼**的局部量，所以：

```
localRotation(bone) = clamp_angle(worldAngle(bone) - worldAngle(parent(bone)))
```

基准帧里各骨骼的世界角即静止姿态角。低置信度关键点（`score < confidenceThreshold`）
不参与角度计算，回落到父骨骼角度或静止值，保证不产生 NaN。
一帧里高置信度关键点少于 `minConfidentKeypoints`（默认 6）时，该帧标记为 `valid = false`。

## 7. 基准帧选取与传播

对应原版 `GetBaseFrame` / `baseBones` / `PropogateList`：

1. **选基准帧**：优先「有效骨骼数最多」，其次「整帧置信度最高」。
   用户显式指定 `baseFrame`（≥0）时以指定值为准，`-1` 表示自动。
2. **推导静止姿态**：以基准帧的关节点算各骨骼长度、肩/髋在躯干坐标系里的局部偏移。
3. **传播**：某帧某根骨骼无效（关键点缺失/低置信度）时，用基准帧（或上一有效帧）的值填补，
   于是整段动画没有空洞；被填补的帧仍然保留 `validity` 标记，供 UI 提示。

## 8. 导出：Spine JSON + Atlas + PNG

### 8.1 结构

`spine.rs` 写出 Spine 4.3 skeleton JSON。**格式版本锁在 `4.3.23`**（`spine::SPINE_VERSION`，
全仓库唯一一份）：官方运行时只按「大版本.次版本」判定兼容，4.3 的运行时读 4.3.x 的
数据既不报错也不警告，但下游工程、审核和复现都希望看到固定值，所以不跟着 npm 运行时
依赖的 patch 号漂。TS 侧的两种导出都从这里取：视频帧图集由 Rust 直接写入，
角色工程由 `engine.spineVersion` 传入 `bakeCharacterProject` 覆盖角色自带的值
（官方示例骨架写的是 `4.3.75-beta`，导出后统一成 `4.3.23`）。

```jsonc
{
  "skeleton": { "hash": "...", "spine": "4.3.23", "width": 1920, "height": 1080, "images": "./" },
  "bones": [ { "name": "root" }, { "name": "hip", "parent": "root" }, ... ],
  "slots": [ { "name": "video", "bone": "root", "attachment": "frame_0000" } ],
  "skins": [ { "name": "default", "attachments": { "video": {
      "frame_0000": { "type": "region", "x": 0, "y": 0, "width": 1920, "height": 1080 }, ... } } } ],
  "animations": { "video": {
      "slots": { "video": { "attachment": [ { "time": 0, "name": "frame_0000" }, ... ] } },
      "bones": { "hip": { "rotate": [ { "time": 0, "value": 12.3 }, ... ] }, ... } } }
}
```

为什么是 4.3 而不是 3.8：官方在 npm 上只发布 4.x 运行时
（`@esotericsoftware/spine-webgl`），要让**浏览器里能直接用官方运行时播放**，
导出格式就得跟着运行时的大版本走。4.x 与 3.8 的差异只有三处：
`skins` 从对象变成数组、region 附件要显式写 `type`、旋转时间轴的键名从 `angle` 变成 `value`。

要点：

- **骨骼**：`x/y/rotation/length` 来自基准帧的静止姿态。
- **旋转时间轴**：每条 `rotate` 时间轴逐帧一个关键帧，`time = frameIndex / fps`，`value` 是第 6 节的局部旋转角。
- **附件时间轴**：每一帧视频画面作为一个 region 附件（默认皮肤 `default` 下的 `video` slot），
  动画用 `slots.video.attachment` 逐帧切换，于是「播放动画 = 播放原视频 + 骨架跟随运动」，
  这与原版 `CurrentBoneLayoutToTexture` 的思路一致（原版逐帧把视频画进图集，再按帧切附件）。
- 空动画会被拒绝（避免产出不可用的 skeleton 文件）。

### 8.2 帧装箱（atlas.rs）

用**天际线/货架**策略把 N 张同尺寸帧排进一张图集：

- 每行的宽度受 `maxWidth` 限制（边长向上取到 2 的幂），逐行放置；
- 记录每帧 `(x, y, width, height, index)`，保证互不重叠且不越界；
- `build_atlas` 生成 Spine `.atlas` 文本，包含 `size: <w>,<h>`、`format: RGBA8888`、
  `filter`、`repeat`，以及每个 region 的 `rotate: false / xy / size / orig / offset / index` 行；
- `src/core/export.ts` 按布局把每帧 draw 到离屏 canvas 的对应位置，得到 PNG，
  再用 `fflate` 把 json / atlas / png 打成 zip 下载。

### 8.3 浏览器里实时播放导出的工程

导出之后不用离开页面：`src/core/spine-preview.ts` 把**刚导出的三件套**直接喂给官方运行时
（`@esotericsoftware/spine-webgl` 4.3）：

```
导出 JSON 文本 ──SkeletonJson.readSkeletonData──┐
导出 atlas 文本 ──TextureAtlas───────────────┤──> Skeleton + AnimationState ──> SceneRenderer(WebGL)
导出图集 PNG   ──GLTexture────────────────────┘
```

几个实现要点：

- **一份数据两处用**：图集只拼一次，实时预览与 zip 导出共用同一个 bundle，
  导出因此是瞬时的；改了导出参数才需要重拼（UI 会提示"参数已改，重新生成"）。
- **纹理**：`TextureAtlas` 在 4.x 里不再接收加载回调，构造完要自己
  `atlas.pages.forEach(page => page.setTexture(texture))`。
- **非预乘 alpha**：我们的图集是直通 alpha，所以 `GLTexture(..., pma=false)`。
- **取景**：相机 `zoom = max(帧宽/视口宽, 帧高/视口高) × 用户缩放`，
  保证竖屏视频也能完整落在画布里。
- **踩过的坑**：如果导出的 JSON 还是旧的 3.8 格式，4.3 运行时**不会报错**，
  只是 `skins` 读不出来 → slot 的 attachment 为 `null` → 画布全黑。
  这类"静默失败"最费时间，所以格式升级后务必重建 WASM/napi/CLI 三个产物。

### 8.4 演示角色：把姿态实时重定向到 Spine 角色

舞台右侧是一个真实的 Spine 角色（内置 Spineboy，也可以换成自己上传的工程），它**跟着视频或摄像头实时动**。
实现分两块：

**实时推理回路**（`src/core/live-driver.ts`）：

```
rAF 循环 ──每 1/15 秒──> drawImage(video) → 取 ImageData
        → Rust preprocess → ORT 前向 → Rust decodePoses
        → Rust smoothPoses（小滑动窗口）→ Rust posesToBones
        → 回调 { pose, rotations }
```

实测单帧 19–28 ms（MoveNet 192×192、单线程），15 fps 的实时跟随完全跟得上；
视频暂停时回路自动空转，不做无意义推理。

**重定向**用的是「加法式局部旋转」——角色骨骼的长度、朝向、绑定姿势都和我们推算的骨架不同，
所以只搬运相对基准帧的转角增量：

```
角色骨骼.rotation = 角色静止角 + (当前帧局部角 − 基准帧局部角)
```

因为两侧的骨骼树都是链式的，逐级叠加同样的增量，整条链就会跟着人摆动，
不需要标定骨骼长度或朝向。没有检测到人体时，角色回到自己的待机动画（Spineboy 的 `idle`）。

这里有两个非常容易踩的坑，都会让角色"看起来只是在播自己的待机动画"：

1. **待机动画会把骨骼角度覆盖回去**。渲染循环里 `AnimationState.apply(skeleton)` 每帧
   把动画的关键帧写进骨骼，如果它和姿态驱动同时生效，我们设的角度立刻被冲掉。
   所以一旦进入驱动状态就先 `state.clearTracks()`，并且只在待机时才 `apply()`。
2. **取景也不能每帧算**。算骨架包围盒要先 `setupPose()` 复位，同样会清掉驱动写入的角度。
   包围盒只在角色加载时算一次，之后只改相机的 position/zoom。

另外给单根骨骼的转角增量加了 ±60° 限幅：低置信度帧偶尔会让关节角跳几十度，
夹住之后动作才像人。

| 角色       | 来源                                    | 映射到的骨骼                                |
| ---------- | --------------------------------------- | ------------------------------------------- |
| Spineboy   | Spine 官方示例 `examples/spineboy`      | torso / head / front-、rear- 的上臂与大小腿 |
| 上传的工程 | 导出面板里选的 zip / json + atlas + png | 由 `guessRig` 从骨骼名猜（见 8.6）          |

角色也可以由用户上传（zip，或多选 JSON + atlas + PNG），此时骨骼映射交给 `guessRig` 猜，
详见 8.6。

> 多页图集：有的工程把部件拆成独立 PNG（页名形如 `images/tail-fin.png`），
> 所以每页要各自挂一张贴图；页名要拼到角色目录下才能取到图片。

内置 4 个官方示例角色（Spineboy / Mix & Match / Celestial Circus / Goblins），素材放在
`public/demo/<名字>/`，每个目录都随附官方 `LICENSE.txt`（可再分发、不可商用）。加载这几个
角色时又踩到两个坑，都在 `createCharacterStage` 里修掉了：

1. **默认皮肤可能是空壳**。`mix-and-match` 的身体在 `full-skins/boy` 里、`goblins` 的身体在
   `goblin` 里，只挂默认皮肤的话画不出东西——更隐蔽的是 `skeleton.getBounds()` 会返回
   `Infinity`，取景函数据此算出荒唐的缩放，角色要么黑屏要么被放大到只剩一条腿。
   现在角色可以声明 `skins: [...]`（按名字叠加），没声明的走启发式：默认皮肤的附件数少于槽位数的
   1/4 时，自动补一个不以 `accessories/` 开头的皮肤；同时给包围盒加了兜底（不是有限值就退回
   骨架自己声明的 `width/height`）。
2. **预乘 alpha 的图集**。官方示例里不少文件名带 `-pma`，图集里写着 `pma: true`。
   贴图按预乘方式上传才对（`GLTexture(context, image, page.pma, false)`），
   否则半透明边缘会发暗。`page.pma` 是运行时解析图集文本得到的，不用额外配置。

### 8.6 角色工程导出：把"视频里检测到的骨骼"搬到角色上

上面 8.1–8.3 说的导出，产物是"视频画面本身"：每帧一个 region 附件，骨骼只是摆放它们的
坐标系。另一种需求是"**用真人动作驱动我自己的角色**"，所以导出面板给了两种模式
（`src/core/character-project.ts`）：

| 模式       | 骨架 / 美术        | 动画                                               |
| ---------- | ------------------ | -------------------------------------------------- |
| 角色工程   | 角色自己的         | `<动画名>.bones.<角色骨骼>.rotate`（视频检测结果） |
| 视频帧图集 | 视频画面，每帧一图 | 只有 slot 的 attachment 时间轴                     |

角色工程这条路的输入是**同一份检测结果**（`result.animation.frames`，逐帧 × 14 骨骼的局部旋转角），
不是视频像素。烘焙公式与实时预览完全一致：

```
角色骨骼.rotation(第 i 帧) = 角色骨骼静止角 + clamp(第 i 帧局部角 − 基准帧局部角, ±maxDelta)
```

加法式的好处是不必知道角色的骨骼长度、朝向和绑定姿势；限幅 ±60° 是为了不让低置信度帧
把四肢甩出去。全程不动的轨道会被跳过（Spine 里少一堆没用的轨道），一根都没映射上时直接报错，
而不是导出个空工程。打包时骨架 JSON、atlas 文本、各页 PNG 全部原样来自角色，只把
`animations` 换成新烤的那条。

**骨骼名怎么认**（`guessRig`）——三种常见写法都认：

| 写法                      | 例子                                       | 侧别              |
| ------------------------- | ------------------------------------------ | ----------------- |
| 前缀式（Spine 官方示例）  | `front-upper-arm` / `rear-thigh`           | front→右、rear→左 |
| 后缀式（本项目 Q 版角色） | `arm-l` / `leg-r`                          | `-l`→左、`-r`→右  |
| 标准式                    | `upperArm.L` / `upperLeg.R` / `lowerLeg.L` | `.L`→左、`.R`→右  |

`front-` 判成右侧是刻意与内置 Spineboy 的映射对齐的：Spine 官方示例里 front/rear 表示
"离镜头近 / 远"，不是左右。两处不一致的话，同一个工程内置跑和上传跑会得到镜像的动作。

这条路上踩到过三个坑，都属于"不报错但结果不对"的类型：

1. **atlas 页块认错**。图集文本是「名字行 + 若干 `key: value`」的块序列，页块和 region 块长得像：
   有的工程页属性不缩进、region 里也有 `size:`；官方示例的页块缩进、且**没有** `format:`。
   只按缩进或只按 `format:` 判断，都会让"导出的 zip 里一张图都没有"。现在靠键判断：
   有 `format/filter/repeat`，或有 `size:` 且没有任何 region 独有键（`bounds/xy/rotate/offsets/index`）。
2. **空动画名会直接抛异常**。上传的工程往往只有一条自己命名的动画，没有 `idle`；
   这时 `findAnimation("")` 会抛 `animationName cannot be null.`，整个角色加载失败。
   现在 `pickIdleAnimation` 在没得挑时返回 `null`，不传空串。
3. **映射到不存在的骨骼会被静默跳过**。`spineboy-pro` 的手臂是整节画的，没有 `*-lower-arm`；
   内置映射里多写两根就会让界面上的"映射了几根"和实际对不上，所以内置配置只写它真有的骨骼。

### 8.7 让导出的工程在 Spine 编辑器里直接打开

导出的工程在网页预览里能播，不等于在 Spine 编辑器里能看。中文命名的角色工程
（`skeleton.images: "./images/"` + 图集页名 `images/tail-fin.png` + 部位名全是中文）
导出后在 Spine 里就是满屏 `MISSING`，原因有三个，导出阶段各修一道
（`normalizeCharacterProject`）：

1. **`skeleton.images` 会被编辑器拿去拼路径**。编辑器把 `images` 目录拼在页名前面，
   `./images/` + `images/tail-fin.png` 就变成 `images/images/tail-fin.png`——
   文件根本不存在，于是所有附件都成了 `MISSING`。导出时直接去掉这个字段
   （官方示例 `spineboy-pro.json` 里也有同样的写法，但在本仓库的目录结构下同样会踩），
   并把页图片**平铺到工程根目录**，页名只留文件名，任何拼法都能落到真实文件上。
2. **非 ASCII 部位名**。部位名（region / slot / 附件名）原本是中文（`角2`、`后发`、`左耳`…），
   跨工具读写同名的东西时最容易出问题。导出时按"这个 region 落在哪一页"把名字换成
   **该页的文件名**——那些 `images/*.png` 本来就是 SeeThrough 风格的英文部件名，
   所以映射是一一对应、不用猜语义的：

   | 原部位名 | 导出后        | 依据（所在页）           |
   | -------- | ------------- | ------------------------ |
   | 角2      | `tail-fin`    | `images/tail-fin.png`    |
   | 角1      | `dorsal-fin`  | `images/dorsal-fin.png`  |
   | 后发     | `hair-back`   | `images/hair-back.png`   |
   | 左耳     | `ear-l`       | `images/ear-l.png`       |
   | 左上眼皮 | `upper-lid-l` | `images/upper-lid-l.png` |

   映射同时对骨架 JSON 的键与字符串值生效（槽位名、附件名、动画里的 attachment 时间轴、
   draw order 里的槽位名都一起改），所以内部引用不会断。已经全英文的工程原样保留。

3. **自己排版图集文本会把 region 弄丢**。Spine 的图集是按行读的，第一版重写实现
   在块之间补了空行，结果编辑器/运行时都找不到 region（`Region not found in atlas`）。
   现在只替换**名字行**，其余行一字不动，行号、缩进、空行全部保持原样。

验证方式不是肉眼比对，而是让**官方运行时**去加载导出的工程：
`new TextureAtlas(atlasText)` + `AtlasAttachmentLoader` + `SkeletonJson`，
只要有一个附件在图集里找不到，就会直接抛 `Region not found in atlas`——
这正是 Spine 里 `MISSING` 的同一套判定，在 `tests/character-project.test.ts` 里。

修旧产物可以不动网页，直接跑脚本：

```bash
node_modules/.bin/jiti scripts/normalize-export.ts <旧导出目录> <新导出目录>
```

### 8.8 界面语言（i18n）

界面支持 **中文 / English / 日本語**，顶栏切换、写进 localStorage。**默认 English**——
仓库面向英文读者，所以刻意不跟随浏览器语言；用户切过之后记住他的选择，并同步 `<html lang>`。

实现刻意保持"零依赖"（`src/i18n/`）：一张 `key → { zh-CN, en, ja }` 的文案表，
加一个模块级 store + `useSyncExternalStore` 的小 hook。

- **组件**用 `useI18n()` 拿 `t`，切语言自动重渲染；`t()` 的入参类型是文案表的 key 联合，
  写错 key 在编译期就报错。
- **非组件代码**（`useSpinevext` 的状态机）直接 `import { t }`，读的是同一个模块级当前语言。
- 状态栏消息存的是 **key + 参数**而不是翻好的字符串——否则切语言时已经显示的那句会停在旧语言。
  参数用 `{name}` 占位符，`t(key, params)` 里做替换。

两道防漏：

1. `tests/i18n.test.ts` 检查**三语的 key 是否齐全、占位符是否对齐**（少一列、写错
   `{count}` 都会红）；
2. 同一个测试会扫 `src/App.tsx`、`src/components/*.tsx`、`src/hooks/useSpinevext.ts`，
   去掉注释后只要还出现中文就报错——防止有人绕开 `t()` 直接写死。

只有界面文案进翻译流程；Rust 内核抛出的诊断性报错（参数解析失败、ONNX 加载失败等）
保持原样，它们是给排错看的。

README 也是多语言的：[`README.md`](../README.md)（中文）、
[`README.en.md`](../README.en.md)、[`README.ja.md`](../README.ja.md)，三份顶部互相链接。

验证方式不是造假数据：`tests/character-export.integration.test.ts` 先让纯 Rust CLI 真跑
`.test-assets/person-rot.mp4`（90 帧），把它导出的 Spine JSON 还原成逐帧骨骼矩阵，再调用
浏览器导出时用的同一份 `bakeCharacterProject` / `packCharacterProject`，然后解 zip 断言：

- 包里只有 `spineboy-video.json` / `spineboy-video.atlas` / `spineboy.png`，没有任何 `frame_*`；
- 图片字节与角色图集一致；
- 动画的骨骼名都是角色的（`front-upper-arm` …），每条 90 个键，至少有骨骼真的在动；
- 键值逐帧等于「角色静止角 + clamp(视频里的相对转角)」。

实测产出（90 帧、8 根骨骼、15 fps）：`torso` 摆幅 22.9°、`rear-upper-arm` 68.1°、
`rear-shin` 60.0°（撞上限幅），zip 304 KB，可以在 Spine 编辑器里直接打开。

## 9. Rust 与外部的三处边界

同一份 `spinevext-core` 被绑定三次，算法一行都没有重复：

| 场景                 | 绑定方式                                      | 产物                       | 推理运行时            |
| -------------------- | --------------------------------------------- | -------------------------- | --------------------- |
| 浏览器（HTML5 应用） | `wasm-bindgen`，`wasm32-unknown-unknown`      | `src/wasm/pkg/*.wasm`      | onnxruntime-web       |
| Node / 批处理 CLI    | `napi-rs`（`crates/spinevext-node`）          | `native/*.node`            | onnxruntime-node      |
| 纯 Rust CLI          | 直接作为 crate 依赖（`crates/spinevext-cli`） | `target/release/spinevext` | tract-onnx（纯 Rust） |

- 构建：`vp run wasm` / `vp run native`；两者都只做一层薄封装。
- 大块二进制（RGBA 帧、模型输出）用**类型化数组切片**传入，避免多次拷贝。
- 结构化参数/返回值统一用 `serde-wasm-bindgen`，Rust 侧 `#[serde(rename_all = "camelCase")]`
  与 `src/core/types.ts` 一一对应。
- 导出函数：`version / keypointNames / transformFor / preprocess / preprocessLetterbox /
decodePoses / decodeRegression / smoothPoses / posesToBones / buildAnimation /
buildSpineJson / packFrames / buildAtlas`。
- 两个绑定的细节差异：`Option::None` 在 wasm 侧显式配置成 `null`
  （`serialize_missing_as_null`），在 napi 侧是 `undefined`；类型上都写成可选。

## 10. 纯 Rust CLI：为什么要在运行时"剪图"

`crates/spinevext-cli` 不依赖 Node、不需要 ONNX Runtime，只用 `tract-onnx` 跑推理。
实现过程中踩到一个必须记录下来的坑——**tract 在这个 MoveNet 导出图上会内存爆炸**：

| 阶段                              | 现象                                                                                                                 |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `model_for_path`                  | 0.01s，正常                                                                                                          |
| `into_typed()`（类型/形状推导）   | 单核 100% 跑满、RSS 从 0 涨到 **5GB** 仍未结束；换 `into_optimized()` 时实测顶到 **24GB** 并把系统打进 19.7GB 交换区 |
| 加 `with_input_fact` 钉死输入形状 | 无改善（说明爆炸来自图内部而非输入）                                                                                 |
| 跳过 `declutter` / `optimize`     | 仍然相同                                                                                                             |

根因是 tf2onnx 导出的图带有两类 tract 处理不好的结构：

1. **数据相关的后处理尾巴**：`ArgMax` / `GatherNd` / 依赖运行结果的 `Reshape`、`floordiv`、`mul`
   ——正是把 heatmap 变成 `[1,1,17,3]` 的那段；
2. 图首归一化前缀里的 `unstack → Slice`，tract 给它推错了形状事实。

**解法**：在 Rust 里对 ONNX 做一次字段级裁剪（`onnx_trim.rs`，手写极简 protobuf 读写，
其余字节原样保留）：

- 从 `kpt_heatmap_0/conv2d_5/BiasAdd`、`kpt_offset_0/conv2d_7/BiasAdd` 两个卷积输出反向求闭包，
  只保留主干节点，把整段后处理尾巴删掉；
- 顺带把归一化前缀也删掉，把图输入改写成"归一化之后、轴变换之前"的 NHWC 张量，
  归一化 `(x - 127.5) / 127.5` 改由 Rust 预处理完成。

剪完之后：解析 0.01s、类型推导 0.01s、**图优化 0.05s**、编译执行计划 0.05s。

顺带一个反直觉的结论：**同一个优化器，在原始图上会吃掉 20GB+ 内存并跑不完，
在图剪干净之后只要 0.05 秒**。所以命令行版默认策略是「剪过图就开优化」：

| 配置                  | 30 帧推理耗时            | 内存峰值 |
| --------------------- | ------------------------ | -------- |
| 原始图 + 优化器       | 跑不完（24GB，进交换区） | —        |
| 剪图 + 跳过优化       | 5.6s                     | 252MB    |
| 剪图 + 开优化（默认） | **1.0s**                 | 212MB    |

两种配置导出的骨骼曲线**逐帧完全一致（最大偏差 0.00°）**——优化只影响速度，不影响结果。

解码则完全复用内核里已有的 `decode_poses`（heatmap argmax + offsets + NMS），
与浏览器版 PoseNet 路径是同一份代码，只是把 `offset_in_pixels` 设为 `false`
（MoveNet 的 offsets 以 heatmap 格为单位）。

### 10.1 与 ONNX Runtime 版的一致性验证

同一段视频分别用「纯 Rust CLI（剪图 + tract）」与「Node CLI（完整模型 + ORT）」导出，
对比 Spine JSON 里每根骨骼的 `rotate` 曲线（2 秒 / 30 帧）：

| 骨骼                                | 最大偏差 | 平均偏差 |
| ----------------------------------- | -------- | -------- |
| `torso`                             | 0.57°    | 0.18°    |
| `head` / 右侧手臂 / 右腿 / `foot.R` | ≤2.6°    | ≤1.6°    |
| 左侧手臂 / 左腿（画面中被遮挡）     | 较大     | —        |

右侧肢体一致到 1° 以内说明两条链路的解码与骨骼映射是等价的；左侧偏差来自那些**低置信度关节点**
——不同推理引擎的卷积实现有微小数值差异，argmax 落在相邻格就会让短骨骼的角度跳几十度。
这类点在任何实现里都属于"该被置信度过滤掉"的部分。

## 11. 与原版的差异（诚实说明）

| 项目     | 原版                                 | 本实现                                             | 影响                              |
| -------- | ------------------------------------ | -------------------------------------------------- | --------------------------------- |
| 姿态模型 | ResNet50-PoseNet（Barracuda，~90MB） | MoveNet SinglePose Lightning（ORT，9.4MB）         | 精度同量级；本实现只出单人姿态    |
| 推理后端 | Unity.Barracuda（CPU/GPU compute）   | onnxruntime-web（WASM SIMD，可选 WebGPU）          | 浏览器内可用，无需插件            |
| 视频解码 | AVProVideo（Windows 原生）           | HTML5 `<video>`                                    | 依赖浏览器 codec（H.264/VP9/AV1） |
| 导出     | 写本地磁盘（SimpleFileBrowser）      | zip 下载 / File System Access API                  | 网页沙箱限制                      |
| 多人     | `DecodeMultiplePoses` 支持多人       | MoveNet 路径单人；PoseNet heatmap 路径保留多人 NMS | 需要多人时替换为 heatmap 模型     |
| 运行形态 | Windows 桌面单机                     | 浏览器应用 + Node CLI + 纯 Rust CLI 三种入口       | 同一套内核，按场景选入口          |

## 12. 局限与后续方向

- 模型只认人体结构：内置的 MoveNet SinglePose 是 COCO-17 人体关键点模型，非人形 / Q 版
  （三头身、多足多翼）、缺色 / 剪影 / 低对比、遮挡的素材都会明显退化，需要换成更合适的
  关键点模型（MoveNet MultiPose / YOLO-pose / RTMPose / ViTPose / DWPose），或者干脆用
  自定义关键点定义。接入点与取舍写在 README 的「检测模型的能力边界」一节。
- 单人模型：画面里出现多人时只输出置信度最高的一人（原版可多人）。
- 角色工程导出目前只在浏览器/Node 侧：纯 Rust CLI 出的是"视频帧图集"那一种
  （角色工程要读官方 Spine 运行时的骨架结构，Rust 侧还没有对应绑定）；骨骼角度本身仍由同一个 Rust 内核算。

- 若视频帧率很高、时长很长，建议调大 `detectEveryNFrames`，推理耗时与帧数成正比。
- 后续可替换为 MoveNet Multipose 或 YOLOv8-Pose ONNX（同 17 关键点），只需改 `inference.ts` 的输出解析。
